# CLAUDE.md

Guidance for working on the MZPico-800-Manager: the Z80-side menu and file
explorer embedded into the MZPico firmware (this repo is the firmware's
`external/manager` submodule). Build with z88dk (`z88dk.zcc` on PATH, snap
channel `--beta` like CI); `cmake` + `make` produce `menu.mzf` and
`explorer.mzf`, with `.lis`/`.map` listings next to them. `check_tail.cmake`
fails the build when a program's BSS end leaves less than 1 KB below the
stack at 0xD000.

Firmware-side protocol reference: the `unicard` device in MZPico-firmware
(`src/mz_devices/unicard.cpp`, `docs/unicard-migration-plan.md`).

## Facts that must hold (2026-09)

Two z88dk programs embedded into the firmware: **menu** (`mz-comm.c`+`console.c`+`menu.c`, served at boot as the SRAM-card image `@menu`) and **explorer** (`mz-comm.c`+`console.c`+`manager.c`+`explorer.c`, `@explorer`). Explored in depth 2026-09-07; facts below come from the sources, the z88dk `+mz` runtime and the `.map` files (`--list -m` write `.lis`/`.map` next to the `.mzf` in `<builddir>/external/manager/`; the copies in the submodule root are stale leftovers, gitignored).

- **Build/runtime**: `zcc +mz -create-app -pragma-define:REGISTER_SP=0xd000` (classic lib, `-lm`, `ENABLE_TEST` defines `MZ800PICO_TEST` which no source uses). ORG `0x1200`; `-create-app` writes a `.mzt` = MZF with the 128-byte header (name from the output name, uppercased: `EXPLORER`, `MENU`), renamed to `.mzf` by CMake. The crt zeroes BSS (classic `crt_initialise_bss`) and sets SP=`0xD000`; `exit()` jumps to the monitor (`$AD`). Everything runs in **MZ-700 mode**: VRAM chars at `0xD000`, attributes at `0xD800` (attr = fg*16+bg, `ATT()`), 40x25. The manager's own CI builds with the z88dk snap `--edge` (build.yml) but releases and the firmware CI use `--beta` — the release explorer bytes differ from a local edge build (harmless so far) and are only reproducible against the same beta snap.
- **Memory map (explorer, from the map)**: code `0x1200-0x3BBB`, data `0x3BBB-0x3CBB` (`vram_codes` table), BSS `0x3CBB-0xC4F0` — dominated by `entries[930]` (37 B each = 34,410 B at `0x3D61-0xC3EB`) and `path[255]`; the stack grows down from `0xD000`, so only **~2.8 KB separate BSS from the stack** — no large locals, no recursion, and `MAX_ENTRIES` cannot grow. Menu: code to `0x2EF8`, BSS to `0x3A20` (`menu[18]`, `config[23]` = 1840 B). The loader (`read_and_execute`) copies itself to `0x1000-0x10xx`, uses SP=`0x10F0`, streams the header to `0x10F0` and the body to `0x1200` over the running program, so it must stay position-independent (only `jr` and absolute ROM/RAM addresses — **no `call` to its own labels**) and under ~0xE0 bytes; it clobbers the monitor work area at `0x1000-0x116F`, which the ROM re-initializes on the way out. `jp 0xECFC` (ROM relocate-and-execute) wants HL -> the header's size field (`0x1102`), BC' = `0x0600`, SP = `0x10F0`; it handles BASIC's load/exec `0x0000` header by moving the body down after remapping. A verification pass over the loaded image costs ~60 T-states/byte ≈ 0.7 s for BASIC — that is why loads are not checksummed (`cmdX_SERVEDSUM` exists for a diagnostic loader).
- **Naked-asm conventions** (`__smallc __naked` functions in `mz-comm.c`/`console.c`): arguments are pushed left-to-right, so after `push iy; ld iy,4; add iy,sp` the LAST argument is at `(iy+0)`, the previous at `(iy+2)`... Return values in HL (`ld l,a; ld h,0`). Callees clobber everything but IY/IX. `__asm` blocks pass through cpp: **an apostrophe in an asm comment silently kills macro expansion for the rest of the block** ("undefined symbol: UC_CMD_PORT" — cost a build today). `inir`/`outir` block transfers put the B counter on A15-A8 (visible in the firmware trace as the high byte).
- **Keyboard** (`inkey()`, since 2026-09-07 a port of Sharp BASIC's GETL handling, MZ-2Z046 A0B21..A0C68): the whole 8255 matrix is scanned every call in assembler (strobe `0xE000`, rows `0xE001`, ~5 us settle, two reads ORed, column 8 = SHIFT/CTRL masked except BREAK); any change restarts a window of 8 identical scans (debounce, ~8 ms at ~1 ms/scan); after a stable window a newly pressed bit is reported at once and the ROM (`getk()` = monitor `$001B`) is called ONCE to decode it; a held key repeats after 64 windows (~0.55 s) and then every 6 (~20/s); no key resets; F-keys (column 9, bits 7..3 = F1..F5, decoded from the matrix) never repeat. **Do not poll `getk()` for levels**: the ROM reports a held key only intermittently, so a level debouncer on it needs long presses and never repeats (rc7/rc8 of v0.4.0). ENTER reaches `getk()` as `0x66` mapped to 13 or 10 depending on z88dk's `STANDARDESCAPECHARS`; `explorer_handle_key` accepts both. Codes: `0x11` down, `0x12` up, `0x13` right = +20, `0x14` left = -20, `1` F1 info panel, `2` F2 cycle device, `3` F3 mount manager (drives 1-4/QD via FDDMOUNT, `cmdX_MOUNTS` 0x98 lists them), `4` F4 recent launches, `5` F5 back to `@menu`; the explorer persists its last location and 8 recent launches in `mzpico.sav` (sd:/ first, flash:/ fallback, like the ini) (676 B struct, `MZX1` magic) written at every launch and directory change; `A-Z`/`0-9` = incremental case-insensitive prefix search (`MAX_SEARCH` 16), reset by cursor moves. `wait_key()` = all keys up, then a new press.
- **Console**: direct VRAM writes through the ASCII->Sharp display-code table `vram_codes`; `put_multi_char_xy`/`put_multi_attr_xy` fill via LDIR; `scroll_up/down(first, n)` move whole 40-byte rows (used for one-line list scrolling); `border()` = `OUT (C),A` with BC=`0x06CF` (GDG border register); `beep()` = `jp 0x0577` (monitor, tail call so it returns to the caller's caller — fine); `clrscr()` clears chars to 0 and attrs to `0x71`.
- **ROM entry points used**: `0xE44A` floppy boot (`FLOPPY_BOOT_ENTRY` in the disassembly), `0xE9B7` Quick Disk boot, `0xE945` tape load, `0xE93B` monitor, `0xE8D5`/`0xEB13` FD/QD presence checks (Z = present; the menu calls them to hide the F/Q entries), `0xECFC` relocate+execute, `0x03C3` hex print, `0x0006` newline, `0x001B` get key, `0x0577` beep. DSK/MZQ execution = FDDMOUNT on the Pico, then `jp` into the ROM boot — it never returns to the manager.
- **Unicard client (`mz-comm.c`)**: every status read is `STSR` + `INIR 4` from `0x50` (`uc_status4`); `check_error` spins on status bit 6 (cloud in progress) and maps error byte 2 / FatFS byte 3 to text in `error_description[32]`. `list_dir`: `SETSORT 3` (sort flag ignored by the device, launchable filter on) + `READDIR path`, one 55-byte FILINFO per STSR poll (LFN at 23.. if `[22]`, else the 8.3 name at 9), capped at 930 then `CLOSE`; sorting is `dir_sort`, an insertion sort on the Z80 (`..` first, dirs first, case-insensitive) — O(n²), noticeable past a few hundred entries. `list_dev` parses `LISTVOL` text (`sd:\r` ...) into names without the colon, max 3. `get_config` streams 80-byte key[16]/value[64] records (max 23). `mount_entry`: `.DSK` -> `FDDMOUNT` device 0, `.MZQ` -> device 5, anything else `OPEN` read-only and left open for the loader. WiFi icon: `WIFISTATUS` every 30 `explorer_poll` iterations.
- **menu.c**: built-ins F (floppy), Q (Quick Disk), C (tape), M (monitor) plus ini `[menu]` `key_<c>=Description|action` entries (only `key_`-prefixed keys count; max 18 items, description truncated to 24; action `@menu`/`@explorer`/`@basic` or a path; DSK/MZQ actions boot through the ROM). sccz80 has no closures, so entries dispatch through 18 fixed wrapper functions indexed into `factory_entry_names[]`, whose pointers reference `config[].value` — keep `config` alive. **`execute_with_mount` ignores `mount_entry`'s result**: a typo'd path opens nothing, the loader streams zeros (size 0) and jumps into garbage — known gap, fix = show `error_description` and return.
- **explorer.c**: `select_file(uint8_t)` and `display_item(uint8_t)` take an **8-bit index while `dir_items` is 16-bit** — directories beyond 255 entries wrap the selection (`MAX_ENTRIES` 930 is unreachable in practice); executing a file clears the screen BEFORE `mount_entry`, so on a mount error the frame is gone and only the error line remains; `cycle_device` ends in a busy-wait delay; when WiFi first reports CONNECTED the volume list is re-read and, if the user has not typed yet (or the current listing is empty), the view jumps to the last (cloud) volume; sizes >= 10000 are shown in `k`.
